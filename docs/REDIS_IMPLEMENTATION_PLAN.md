# Redis implementation plan

Phase 1 is an audit and planning phase. No new Redis implementation or API change is made by these documents. Existing public-menu caching remains in place.

1. **Infrastructure and configuration:** retain Spring Boot 3.3.5 and its managed Redis/Lettuce dependency. Add a local Compose example bound to loopback without touching the existing container or its data. Document URL-based host, port, credentials, database and `rediss://` TLS support; assess whether separate environment properties are needed without breaking `REDIS_URL`. Keep secrets outside version control. Validate connection and command timeouts and per-environment namespaces.
2. **Architecture decision:** evaluate moving menu assembly out of the controller and adopting Spring Cache with a typed JSON cache manager. The existing revision-based cache and per-instance request coalescing offer behavior not automatically reproduced by `@Cacheable`; preserve tested failure, invalidation and transaction semantics. Do not add cache regions or annotations merely to meet an example. If Spring Cache is used, explicitly configure serializers, null handling, prefix, TTLs, error handler and transaction ordering; avoid unrestricted polymorphic deserialization.
3. **Consistency and security:** define the acceptable staleness window for public-menu data and separate it from checkout correctness. Test concurrent loads and mutations, Redis outage/recovery, revision loss, transaction rollback, category/menu/store changes and direct-write assumptions. Choose a stronger design only if immediate freshness is actually required. Preserve Spring Security on every protected request and never cache credentials or token state.
4. **Operations:** evaluate Actuator and metrics with a non-public management surface and an optional Redis health contribution that does not mark the application unready by default. Add cache hit/miss, errors and timing if suitable; document monitoring, safe namespace-specific cleanup, memory limits, ACLs and TLS. Do not recommend flushing shared Redis.
5. **Verification:** run existing API/security tests and real Redis tests against an isolated namespace, including create/update/delete, expiry and fallback; test multi-instance behavior and Redis failures. Test MySQL migrations, transaction locking and checkout separately on disposable MySQL. Report actual results and limitations.
6. **Documentation and rollout:** provide setup, environment-specific examples, verification, rollback and troubleshooting. Enable only explicitly selected cache regions, compare measured query load, and avoid API or schema changes unless separately justified.

The existing `PublicMenuRedisIntegrationTest` uses a random namespace and an externally supplied `TEST_REDIS_URL`. Phase 3 prepares a disabled Spring cache manager alongside the existing cache; adopting it requires a separately verified invalidation and outage strategy. Existing tests do not by themselves establish full production behavior. Proceed through subsequent phases with user approval, as requested in the supplied execution strategy.
